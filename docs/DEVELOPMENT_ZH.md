# 开发方式与经验

这里记录从项目中总结的工作方式，不是后续维护计划。

## 先验证最不确定的前提

扩大开发前，先验证最可能使方案失效的最小路径：框架加载、一次只读操作、正常退出、重复启动。已经放弃的不问凡尘内置版实验说明，在加载器本身尚未可用时，不应提前迁移全部功能。

## 将证据绑定到实际文件

将源码身份、EXE／DLL 哈希、压缩包哈希及相关运行时协议一起记录。版本名或基线提交不能代表尚未提交的改动。公开副本可能去除个人路径或缺少受限输入，使用清单和构建说明注明这些差异。

## 先复现，再定向修复

1. 确定失败阶段，保留第一个具体错误。
2. 通过真实构造和首次读取复现，不替换整条待测调用链。
3. 做最小相关修改，覆盖正常状态及错误／变化状态。
4. 未受影响的代码复用有效旧证据；共用生命周期或构建逻辑变化时再扩大检查。

进程与对象身份、字段类型、方法签名、调用约定及数值边界仍按实际操作核验。仅有游戏版本或整文件指纹差异，不能证明所有功能都失效。

## 区分不同层次的验证

| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 静态解析、离线测试 | 代码结构及明确覆盖的路径 | 游戏内实际效果 |
| 运行时只读检查 | 当前状态的定位与读取 | 写入或奖励成功 |
| 修改并立即读回 | 内存即时结果 | 存档及后续计算 |
| 正常保存并重载 | 该流程下的持久化 | 所有活动结算 |
| 活动完成 | 已观察活动的结果 | 全部场景、角色及未来版本 |

人工反馈成功与直接观察分别标明。未测试不等于失败，也不等于通过。

## 共用生命周期与性能

原生功能复用有所有权的统一后台／会话。客户端关闭、脚本变化和宿主升级需要分别核验；重启后可用不能证明残留会话复用已经修复。派发结果不明时，不自动再次写入。

无缓存发现与重复读取分开计时。使用有界扫描及单次读取内经过验证的缓存，清理过期数据并复查身份；不能用跳过保护换取速度。

## 按约定范围结束

避免将小修复扩大成新自动化框架或全功能重测。保留有价值的失败证据，明确哪些新信息能改变判断；没有新依据就停止重复尝试。公开归档不意味着重新启动软件开发或实机测试。
